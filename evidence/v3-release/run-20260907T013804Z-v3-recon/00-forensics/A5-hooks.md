### Double-registrations explained

1. **`stop-guard.sh` on `Stop` + `SubagentStop`** (`hooks.json:16-26,27-37`) — identical hook entry, same script, same 10s timeout, no matcher on either (fires on every stop). The script itself reads `hook_event_name` from stdin (`stop-guard.sh:68-75`, default `"Stop"`) so its own JSON output (`hookEventName` field, and the `emit_off` helper's `_event` param) correctly names whichever event actually fired it. One script, two lifecycle points, self-aware of which one is live.
2. **`bash-write-notice.sh` on `PostToolUse` + `PostToolUseFailure`**, both matcher `Bash` (`hooks.json:92-101,103-113`) — same script runs whether the Bash command succeeded or failed, because a write can happen either way (e.g., a command that partially succeeds then errors). `EVENT = data.get("hook_event_name") or "PostToolUse"` (`bash-write-notice.sh:33`) is read fresh each invocation and echoed back in `hookSpecificOutput.hookEventName` (`bash-write-notice.sh:222-224`), so the notice always names the event that actually fired it.

## The Bash bypass

- **"Bash-authored writes bypass the Write|Edit guards"** — **VERIFIED** (see blind-spot #1 above; matcher separation in `hooks.json` plus corroborating in-source comment).
- **"bash-write-snapshot.sh + bash-write-notice.sh add detection-by-effect via content hashing and never deny"** — **PARTIALLY VERIFIED, with a material HEAD-vs-working-tree distinction the brief's phrasing elides:**
  - "never deny" — **TRUE**, and true at both HEAD and in the working tree. Neither script contains an `exit 2`/deny path in either revision.
  - "via content hashing" — **TRUE at HEAD, FALSE in the current working tree.** The two hook scripts are both `git status`-modified (`M plugins/proofpunk/hooks/bash-write-notice.sh`, `M plugins/proofpunk/hooks/bash-write-snapshot.sh`), each +69/-10 lines vs HEAD (`git diff HEAD --stat`: "2 files changed, 117 insertions(+), 21 deletions(-)"). At HEAD (commit `93c479d`, and unchanged back through `a41591a` which introduced these files), `sha()` computed a true SHA-256 over file content:
    ```python
    h = hashlib.sha256()
    with open(p, "rb") as fh:
        for chunk in iter(lambda: fh.read(65536), b""):
            h.update(chunk)
    return h.hexdigest()
    ```
    The **uncommitted working-tree edit removes this** and replaces it with a stat signature — `f"{s.st_size}:{s.st_mtime_ns}:{s.st_ctime_ns}:{s.st_ino}"` (`bash-write-snapshot.sh:88-103` and mirrored in `bash-write-notice.sh:120-135` as of the working tree). The in-flight change's own comment explains why: *"Content hashing 10k protected files cost 7.8s per pass (15.5s per Bash call) on a real repo and always blew the cap, which silently disabled the guard entirely"* (`bash-write-snapshot.sh:89-91`), and the `LIMIT` was raised from `4000` to `100000` in the same diff (confirmed via `git diff HEAD -- plugins/proofpunk/hooks/bash-write-snapshot.sh`, hunk `@@ -40,19 +43,62 @@`). The rationale for why `ctime` still catches `cp -p`/equal-size substitution despite dropping content hashing is documented and internally consistent (`st_ctime_ns` is kernel-set on any inode/content change and "CANNOT be forged from userspace" — verified-by-comment, not independently re-verified by this lane). **Net characterization of the in-flight change**: a deliberate hash→stat-signature downgrade for a ~400x latency win, plus new `.proofpunk-ignore` prune-list support and a broadened `SKIP_RX` for vendored/venv trees (both diffs identical in `bash-write-notice.sh` and `bash-write-snapshot.sh`, confirmed by `wc`-equal diff sizes and matching hunk headers).
