## Arc 1 — The hook-registration lineage: shipped-but-dead, three times

This is the single most-repeated failure in the repo's history: a hook script exists on disk, is copied by the installer, and is never wired into `settings.json`'s event list, so it fires never.

- **`1cdb8bf`** (2026-08-13, v1.10.0) — original hook system. 5 lifecycle hooks, `tools/test-hooks.sh` (13/13), the installer wires `--hooks`. This is where `evidence-guard.sh` was first written.
- **`96d91d6`** (2026-08-14, v2.0.0) — `cook` merged into `implement`; `no-test-files.sh` becomes a hard PreToolUse block; `stop-guard.sh` gets a scout-record requirement. Claims "19/19 hook cases, verifier PASS @17 skills."
- **`3250a1a`** (2026-08-15, v2.0.1) — "installer hardening proven on real runs": ghost `ALL_SKILLS` list removed, `--hooks` claimed to "merge all 5 hooks idempotently." This claim is what later turns out to be false for a subset of hooks.
- **`99c72fb`** (2026-08-27 17:34:03, v2.2.0) — **the revelation.** The commit body states the root cause plainly: `evidence/AGENTS.md:22` says a modified capture is a fabricated claim; that rule was violated twice in the same session (banners prepended to captures, a re-run overwrote committed ones) and caught by *human review*, not tooling — motivating a new `capture-guard.sh`. Wiring that guard up exposed a structural bug that had been shipping silently since v1.10.0: the settings.json merge treated idempotency **per-event**, not **per-command**. Once `no-test-files.sh` landed in `PreToolUse` for a given event, every sibling hook targeting that same event returned "already present" and was silently skipped — meaning `evidence-guard.sh` had shipped registered-but-dead through v1.10.0, v1.10.1, v2.0.0, v2.0.1, and v2.1.0. The `3250a1a` claim of "merges all 5 hooks idempotently" was therefore false the entire time it was made; nobody had driven a scratch install and read the produced `settings.json` to check.
- **`8718561`** (2026-08-24 21:58:41) — proves the `99c72fb` fix and installer harness with real before/after arms into throwaway HOMEs.
- **`b4bd03a`** (2026-09-04) commit body, "Counts reconciled" section — a related but distinct drift is caught in the same lineage: `AGENTS.md` said 17 skills where the tree has 18; `plugins/AGENTS.md` named 7 hook scripts where 9 exist (7 being the *event-key* count, silently conflated with script count).

**What this arc reveals:** the defect was never in the hook scripts themselves. It was in the *installer's own idempotency logic*, and the only gate that could see it (`tools/test-installer.sh` group 8, added in `99c72fb`) had to be purpose-built to read `settings.json` after a real `--hooks` run — no amount of testing the hook scripts in isolation, or testing the installer's file-copy step, would ever surface it. `d3-gate-inventory.md` F-D3-2 names this explicitly: "installer correctness has a single point of observation. If that one group is skipped, mis-scoped, or vacuous, the installer has *zero* coverage again — exactly the pre-`5e5150b` state."

## Arc 2 — The harness that couldn't see its own subject

- **`2047a9f`** (2026-08-24 20:41:59) — "make install, hook, and harness capable of failing." Three separate instruments (a hook, a harness, an installer step) each "reported success without establishing it." `session-start.sh` had a missing comma making its `SessionStart` payload invalid JSON — the host silently dropped it, and a live session with no doctrine text in its prompt quoted "Proofpunk is installed." verbatim. `test-hooks.sh` grepped for substrings instead of parsing JSON, so it passed on that same malformed payload. The commit's own mutation-check is the proof: reintroducing the missing comma in a sandbox copy yields rc=1 after the fix; before the fix, the same mutation was invisible.
- **`5e5150b`** (2026-08-27 16:30:34, v2.1.0) — "close five defects the harness never covered." "Zero installer coverage is how three green gates coexisted with five real defects" (`--ref` only resolving `refs/heads`, `--hooks` silently exiting 0 without registering anything when `python3` was absent, local installs exiting 0 with an empty skill tree when `tar` was missing, `verify` printing a green tick for frontmatter-less skills when `python3` was absent, silent theme-overwrite).
- **`d3-gate-inventory.md` F-D3-1** (2026-09-02, discovery phase) — **a correction to a correction.** A first draft of this discovery finding called the `5e5150b` root cause "the headline finding" and claimed the underlying defect was *never actually fixed*. That claim is itself retracted in the same document after reading `dry-run-install.sh` end-to-end: its declared subject was never the shell installer — its header states it "execute[s] the `/proofpunk:install` mechanics," i.e. it models the *agent playbook* (`commands/install.md`), which has no shell implementation of its own to invoke. The `5e5150b` remedy, read from `git show -s --format=%B 5e5150b`, was correctly scoped: add `tools/test-installer.sh` to drive the real shell installer, and *correct the mislabelled AGENTS.md row* — not rewrite `dry-run-install.sh` to invoke a program it was never about. `git show --stat 5e5150b -- tools/` confirms `dry-run-install.sh` was deliberately untouched in that commit. The genuine gap that remains, honestly disclosed rather than fixed: `/proofpunk:install` **as a slash command** — the real thing a user types — still has no gate at all. `dry-run-install.sh` proves the merge mechanics deterministically; nothing proves the command-doc-to-agent-execution parity, or that `--platform`/`--clobber`/`--no-rules` behave as documented.

**What this arc reveals:** a harness's name and its stated purpose can both be wrong, and a document one level removed (the discovery register) can *also* get the correction wrong on a first pass before getting it right on a second — the layered self-correction is preserved rather than collapsed, which is itself informative about how confidently-stated findings should be treated.

## Arc 3 — The stop-guard escapes: role-blindness, then substring hazards, then substring hazards again

`stop-guard.sh` is a Stop/SubagentStop hook asserting an assistant does not claim completion without cited proof. It has been broken in at least four distinct, independently-discovered ways across the repo's life:

- **`a41591a`** (2026-09-01 19:31:59) — original defect: the guard scanned **raw JSONL with regex**, never checking `role`. Two consequences: a user's own question containing claim-like language could trigger a false block, and — inverted — a user's own words containing "screenshot" or "touchpoints" could silence the guard for a genuinely unproven *assistant* claim. Fixed by parsing each line as JSON and gating on `role == "assistant"`.
- **`b4bd03a`** (2026-09-04 00:35:24) — **a second, structurally different escape found after the role-fix landed.** Even gated on `role: assistant`, the guard was still matching against the **raw transcript record**, not the assistant's extracted text. Real transcript envelopes carry a `"cwd":"/Users/<you>/<project>"` field, which — because it contains a `/`-separated path — satisfied the `PATH_SHAPED` regex on *every single line*, making the `SCOUT_KEYWORD ∧ PATH_SHAPED` conjunction trivially true regardless of what the assistant actually wrote. Fixed with a new `assistant_text()` extractor that pulls only the message content, with an explicit design note in the diff: "Falls back to `""` so a shape we do not recognize grants no credit rather than silently reverting to raw-line matching" — a fail-closed default chosen deliberately after the fail-open failure mode had just been diagnosed.
- **`b4bd03a`** (same commit) also tightens `PATH_SHAPED` itself: it previously matched any two `/`-separated segments (`"and/or"`, `"input/output"`, bare URLs all qualified as a "file citation"); now requires a trailing extension.
- **`d1ecbb0`** (2026-09-04 00:41:20) — **a third escape**, found immediately after `b4bd03a` landed, by continuing to probe the same guard rather than declaring it done. `PROOF_NONPATH` (the non-file-citing proof form, e.g. "validated OK") accepted the bare two-word phrase "validate OK" with no verification the command it describes ever ran. Tightened to require a command *shape*: `curl` must name an http(s) endpoint alongside its 200; the "validate" form must name `fresh_evidence.py`.
- **`evidence/v3-release/l4-enforcement/run-20260904T043559-scout-substring/VERDICT.md`** (uncommitted pre-work at the start of this task, per the assignment's own ground truth) — **a fourth, distinct escape in the same conjunction**, found by adversarially testing the `b4bd03a` fix rather than trusting it. Even with `assistant_text()` extraction, `SCOUT_KEYWORD` is a plain substring match. A cited evidence path whose *run directory name* happened to contain the literal word "scout" (e.g. `e2e-evidence/run-2026-scout/step-05.png`) supplied both halves of the scout-detection conjunction from itself: the word "scout" from the dirname, the path shape from the path — no actual scout-prose was needed. The VERDICT also records a harness-integrity near-miss: `tools/test-hooks.sh`'s case 23, which was supposed to catch exactly this, had its fixture's run-dir renamed from `run-2026-scout` to `run-2026-plain` at some point *outside this session* (00:32, before the fix), which coincidentally *avoided* the hazard rather than catching it — case 23 passed identically with or without the eventual fix. A new case 24, deliberately re-introducing the `scout`-named directory, is what actually discriminates.

**What this arc reveals:** the same conjunction-based detection logic (`X keyword AND Y shape ⇒ credited`) kept producing new escapes because each fix addressed the specific manifestation found, not the general property (an attacker- or accident-controlled substring should never be able to satisfy a detector meant to recognize the assistant's own reasoning). This is the strongest evidence in the repo for defect class 1 below.

## Defect taxonomy

Four recurring defect classes, each observed multiple independent times across the arcs above. For each: the class definition, every concrete instance found, and a **permanent detector** — a mechanism that would catch any *future* instance of the class, not a fix for the specific instances already closed.

### Class 1 — A harness that structurally cannot fail (false-green by construction)

**Definition:** a test, gate, or guard whose passing tells you nothing about the property it claims to verify, because either it never exercises the real code path, or its detection logic can be satisfied by input that has nothing to do with the thing it is meant to detect.

**Instances found:**
- `tools/dry-run-install.sh` — reimplements the install steps in shell rather than invoking `tools/proofpunk-install.sh`; a green run proves only that the reimplementation is internally consistent (`d3-gate-inventory.md` F-D3-1).
- `tools/test-hooks.sh` (pre-`2047a9f`) — grepped raw stdout for substrings instead of parsing JSON structurally, so it passed against a malformed `SessionStart` payload that the real host silently dropped.
- `stop-guard.sh`'s `SCOUT_KEYWORD ∧ PATH_SHAPED` conjunction — satisfiable by an evidence-path *directory name* alone (the word "scout" in a dirname), independent of whether any scout-prose exists.
- `stop-guard.sh`'s original raw-JSONL role-blindness — a user's own words could satisfy or defeat a check meant to gate the assistant's claims.
- `verify-orchestration.py`'s hardcoded expected-leaf-set — a check meant to catch *drift* was itself a source of drift; it failed on a correct graph change because its own reference value was stale (`b4bd03a`).

**Permanent detector:** for every harness/gate in the repo, require a documented **mutation test** as a precondition for trusting its green state — not a written assertion that it "should" catch a defect, but a captured artifact showing: baseline green → a specific, named mutation of the thing it claims to check → the harness turns red **and names the mutation** → restore → green again, byte-identical. This is already the repo's own convention (visible in nearly every `verdict.json` in `e2e-evidence/`); the detector is to make it a **required field**, checked mechanically: any commit that adds or claims a new harness/gate/guard property, without a linked mutation-test artifact for that exact property, should be flagged for review before being trusted. A `grep`-based CI check that scans new/changed `tools/*.sh`, `tools/*.py`, and `hooks/*.sh` files for a corresponding sibling entry in `e2e-evidence/` referencing a mutation test is a concrete, buildable version of this — cheaper than proving it structurally, and consistent with the repo's own stated preference for deriving rather than restating.

### Class 2 — A hardcoded list drifting from its canonical source

**Definition:** a count, name, or set is asserted by hand in a document, comment, or check, when a canonical machine-readable source for that same value already exists elsewhere in the repo.

**Instances found:**
- The installer's own hook-copy and hook-registration lists were hardcoded separately from `hooks.json`, so `session-start.sh` was silently never copied and 4 of 6 events never registered (`a41591a`).
- Skill/reference/command counts hardcoded across `README.md`, `AGENTS.md`, `tools/INSTALL.md`, `usage-guide.md`, and both manifest pairs — regressed at least four separate times per `plugin-improvements.md`'s own root-cause note ("skill-count strings regressed 4×, `.planning/BUILD-PROMPT.md:103-105`").
- `verify-orchestration.py`'s expected-leaf-set was a hardcoded list rather than derived from what each `SKILL.md` declares (`b4bd03a`).
- The v3 work order's own "9 script registrations" — a hand-restated number that conflated event-key count with registration count, contradicted by the repo's own already-correct `architecture.md:497` (`d6-d7-measurement.md` F-D6-4).

**Permanent detector:** a single CI-runnable script (`tools/verify-counts.py` or equivalent) that walks every canonical source (`hooks.json`, the `skills/*/SKILL.md` glob, `references/*.md` glob, `commands/*.md` glob, `opencode/commands/*.md` glob) once, computes every count this repo has ever hand-restated, and asserts each hand-written occurrence — found by grepping for number-adjacent count-words ("skills", "references", "commands", "registrations", "hooks") in every `.md` file — matches the computed value or is flagged. This generalizes the fix already applied piecemeal in `c39a0f0` and `b4bd03a`; the detector is making the *check itself* permanent and automatic rather than a manual sweep repeated by hand each time drift is noticed.

### Class 3 — A component shipped but never registered

**Definition:** a file exists on disk, is copied by the installer or otherwise deployed, but the mechanism that would make it *active* (an event registration, a router edge, an entry in a discovery table) was never wired, so the component is present and silently inert.

**Instances found:**
- `evidence-guard.sh` — shipped on disk in every `--hooks` install from v1.10.0 through v2.1.0, never actually registered in `settings.json` due to the per-event idempotency bug (`99c72fb`).
- Pre-router state (before `0de4680`) — the plugin had 17 independently-invocable skills and zero entry point; nothing was broken exactly, but nothing linked them together either, matching the operator's "one massive skill that... link[s] with everything else" complaint.
- `references/ci-gates.md` — cited only by the router's own descriptive table, never loaded mid-workflow by any *executing* skill (backlog #16) — closed as a side effect of `a41591a` adding the citation to `production-readiness/SKILL.md`.
- The stale `1.10.1` marketplace-cache tree (`d6-d7-measurement.md` F-D7-1) — present on disk with 19 skills including two dead names (`cook`, `functional-validation`), not registered, therefore inert for doctrine-injection purposes — but any tool that globs the marketplace cache path rather than reading `installed_plugins.json` would see it and be wrong.

**Permanent detector:** for hooks specifically, `tools/test-installer.sh` group 8 (added in `99c72fb`) already is this detector for the registration case — it drives a real `--hooks` install and reads the produced `settings.json`, which `d3-gate-inventory.md` correctly identifies as "the only vantage point from which a copied-but-unregistered hook is visible." Generalize the *pattern*, not just the hook instance: any component with a "shipped" state and a separate "active" state (skills vs. router edges, references vs. citing skills, hook files vs. registered events) needs its own analogous two-state check — enumerate the shipped set from one canonical source, enumerate the active set from a *different* canonical source (the thing that actually consumes it at runtime, not another list describing it), and assert set-equality with named symmetric-difference output. `verify-orchestration.py`'s reciprocal-edge check (does every "Called by" line match a real router entry, and vice versa) is the second working instance of this pattern in the repo; a third, generalized script applying the same shipped-vs-active check to hooks, references, and skill-tree stale-copies in one pass would close this class going forward rather than requiring a new bespoke check each time a new "shipped but not wired" instance is found.

### Class 4 — A claim stated above its proof level

**Definition:** a status is reported (PASS, FIXED, RESOLVED, DONE) using language that implies a stronger verification than what was actually performed — e.g. a script-level check reported as end-user proof, a count of harness invocations reported as a count of improvements, an inference reported as a finding.

**Instances found:**
- "12 probes prove components deliver in live sessions" conflated with "12 improvements fixed" — corrected in the same-day `d433519`.
- "Zero files name cook" — overstated; narrowed to "zero files name the *command*" after checking, in the same-day `f8dccf8`.
- D1 ("the two e prompt") originally headed "RESOLVED (standing fallback confirmed)" at high confidence from tree-absence alone, downgraded to "PRIOR-AGENT INTERPRETATION, medium confidence" once session stores were actually searched (`d1-d2-d8-transcript-evidence.md` superseding `d1-d2-d4-d9-dictation.md`).
- Backlog item #5 (stop-guard PROOF/SCOUT bare-keyword defect) marked FIXED from source-reading alone in an earlier pass, then found still broken when the guard was actually *driven* — corrected in `17733aa`'s VERDICT.md.
